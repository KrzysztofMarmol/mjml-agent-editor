# Agent contract

What every agent backend must implement so the editor can talk to it unchanged. There are two
implementations: `packages/agent-node` (TypeScript, the default) and `agent-python` (FastAPI).
This document is the specification they both answer to.

The machine-readable half lives in `@mjml-agent-editor/core`:

- tool names, descriptions and argument schemas — `packages/agent-core/src/tools.ts`
- the same, as JSON for non-TypeScript implementations — `packages/agent-core/contract/tools.json`
- document addressing every backend must agree on — `packages/agent-core/src/mjml-document.ts`

`contract/tools.json` is generated by the package build, and a unit test fails if it drifts from
the TypeScript source, so it cannot silently go stale.

## Transport

`POST /api/chat`, request body:

```jsonc
{
  "messages": [/* UIMessage[] from the AI SDK */],
  "docId": "uuid",
}
```

The response is an SSE stream in the AI SDK **UI Message Stream** protocol, which is what
`useChat` in `ChatPanel` consumes. Backends do not hand-roll this framing: the TypeScript
implementation returns `result.toUIMessageStreamResponse()`, the Python one uses
`ai.ui.ai_sdk.to_sse` with `UI_MESSAGE_STREAM_HEADERS`.

Validation failures (`docId` missing, body not JSON) return `400` with `{"error": "..."}`.
Failures _after_ streaming has begun must be emitted as an error part inside the stream, never
by dropping the connection — a truncated chunked response surfaces in the browser as an opaque
"network error" with nothing to show the user.

> **Not yet specified: history.** Today the client re-sends the whole conversation on every
> request. Phase 4 moves history server-side (a `sessionId` plus a `chat_messages` table), which
> will change this request shape. It is deliberately not designed here — there is no point
> fixing an interface before the second consumer exists to constrain it.

## Authorization

`docId` arrives from the client and is **not** authorized by the handler. A host serving more
than one user must pass stores that are already scoped — for example a `DocumentStore` bound to
the caller's session that rejects unknown ids. The spike had no scoping whatsoever, which is why
any visitor could read and delete any document.

## Ports

Backends never talk to a database or an image service directly. They receive `DocumentStore`,
`CommentStore`, `ImageProvider` and `MjmlCompiler` (`packages/agent-core/src/ports.ts`). This is
what lets the same agent run against Supabase, plain Postgres or an in-memory store.

## Behavioural rules

These are load-bearing; a backend that skips one will pass a naive smoke test and corrupt
documents in production.

1. **Never persist MJML that does not compile.** Every write tool compiles first (strict
   validation) and returns the compiler output to the model on failure. The model corrects itself
   from that message; this is the main reason the agent rarely leaves a document broken.
2. **Never change an existing `sec-<id>`.** Those ids anchor comments. `set_section` forces the
   target id onto the replacement even when the model supplies a different one.
3. **`set_section` takes exactly one section.** Two concatenated sections must be rejected, not
   merged — they would share one id and the next edit would hit the wrong element.
4. **Tool results are strings.** Errors read as `ERROR: <what happened>` so the model can act on
   them without parsing.
5. **Compiler messages must not leak host paths.** `mjml` interpolates its `filePath` — which
   defaults to the process working directory — into every validation message. Strip it: those
   messages reach both the model's context and the chat panel.

## Open question: multi-line tool arguments

The spike spent roughly a quarter of its system prompt demanding single-line MJML with
single-quoted attributes, plus a retry hint (`_EMPTY_ARG_HINT` in `agent/tools.py`). That was a
workaround for the Vercel AI SDK **for Python** replacing malformed tool-call argument JSON with
`{}`. It is a property of that SDK, not of the task, and it costs output quality — forbidding
newlines inside an `mjml` argument makes the model write worse markup.

The TypeScript implementation therefore ships the clean prompt by default. **This has not been
confirmed against a live model yet** — only against mocked streams. Until it is:

- `buildSystemPrompt({ legacyJsonArgumentHint: true })` restores the old instructions,
- `LEGACY_JSON_ARGUMENT_HINT` in agent-core holds the wording, so both backends share it.

If live testing shows the TypeScript SDK handles multi-line arguments (expected — it parses
streamed arguments incrementally), the Python backend should keep the hint and the contract
should stay clean, since the constraint belongs to the implementation that needs it.

## Conformance

`pnpm test:conformance --url=<chat endpoint>` drives a fixed prompt against a running backend and
asserts the same tool-call sequence and the same final MJML. Run it against both implementations
in CI. _(Not yet written — Phase 1 finishes with it.)_
